Сравнение товаров на маркетплейсе

Требования к фиче «Добавить товар к сравнению»: use case и объектная модель в собственной нотации, где каждый шаг сценария связан с записью в базе требований.

Роль: системный / бизнес-аналитик Артефакты: use case, объектная модель, экраны Версия: 1.1 · Ready
01 · Контекст

Перенести фичу из интернет-магазина в маркетплейс

Сравнение товаров уже было в старом интернет-магазине. Его нужно было перенести на маркетплейс и адаптировать под новую архитектуру каталога.

Главное отличие: в маркетплейсе у одного товара может быть много офферов — предложений разных продавцов и магазинов со своими ценами и наличием. Требования должны были ответить, что именно сравнивается и какую цену показывать.

02 · Ключевые решения

Что зафиксировано в требованиях

1

Сравниваем товар, а не оффер

Можно добавить с карточки товара или с карточки оффера — в список всегда попадает товар.

2

Один список — одна категория

Список сравнения создаётся на основную категорию товара, только 3-го уровня. Имя списка = имя категории.

3

Цена фиксируется при добавлении

С карточки товара — цена основного оффера (ближайший магазин с наличием). С карточки оффера — цена этого оффера. Добавлено в версии 1.1.

4

Ограничения списка

Товар в списке уникален, не больше 20 товаров, список не бывает пустым. Сравнение доступно только аутентифицированному пользователю.

04 · Нотация

Как связаны артефакты

У каждого блока схемы есть тип и поля для кодов связанных записей (_ENTITY_CODE, _FUNCTION_CODE, _VIEW_CODE…).

START / ENDГраницы сценария
ActionДействие пользователя
ViewЭкран — ссылается на запись VW.
SelectРазвилка — условие с ветками Да / Нет
System EventСобытие системы — ссылается на объект и атрибут

База требований в Airtable: у каждой записи код, статус, версия, автор.

UCD

Реестр сценариев: домен, версия, ссылка на схему

OBJ / ENT

Объектная модель: атрибуты, типы, ограничения, права API

FN

Функции: логика, ограничения, связь с сущностью

VW

Экраны и фронтовая логика для web и mobile

NT

Уведомления: триггер, получатель, каналы

Версии

Атрибуты помечены версиями, синхронно с версиями схемы

UCD→шаг System Event→OBJ.CMPLST · атрибут→FN / VW / NT

06 · Итог

Что показывает кейс

  • Мой вклад: use case, объектная модель списка сравнения и логика выбора оффера — моё авторство.
  • Трассировка: от шага сценария можно перейти к конкретному атрибуту объекта и обратно — по коду.
  • Версионирование: изменение 1.0 → 1.1 (фиксация цены) отражено и в схеме, и в атрибутах объекта.
  • Что обезличено: названия сущностей, коды и ссылки заменены. Остальные записи базы — вымышленные демо-данные, их авторы вымышлены. Структура нотации и логика фичи — реальные.
